Gitter 工具属性 × Agent 融合设计

工具面统一稿 —— 不新增功能域，把分散的 MCP 工具集、harness 权限、提交安全网、hunk 三态收敛成一个模型：一套工具、三类客户端、一条闭环，并补上融合缺的拼图：验收状态的人机双向共享。

源文档：docs/tool-agent-fusion.md · 本页为其可视化呈现 · 定位不漂移："AI 生产，人验收，Gitter 管理验收台"

01

融合三命题

"融合"不是加功能，而是三件可以逐条验收的事。命题 1、2 在既有文档已有落点，命题 3 是本稿补齐的拼图。

命题 1

工具出口 agent 化

Gitter 的工具能力成为 agent 可寻址、可组合、可控的调用面——agent 不必再裸解析 git 文本输出。

落点：MCP / CLI / harness 三出口
命题 2

agent 输入数据化

agent 的动作与会话成为 Gitter 工具视图的一等数据（会话卡、溯源徽标、活动指示）——agent 只是一个新的"变更来源"。

落点：provenance / 会话卡 / 任务卡
命题 3

人的裁决共享化

验收三态（接受 / 拒绝 / 待审）成为人机共享状态，反向成为 agent 的输入——agent 知道人对上一轮的裁决。

★ 本稿补齐 · review.state
反融合边界（定位护栏）：Gitter 不做 agent 编排 / 工作流 / 多 agent 调度；不做 inline 补全与内嵌 chat；工具面是薄层，只做能力封装与策略执行；拔掉所有 agent，Gitter 仍是完整 git 客户端（有降级守卫测试）。

03

统一操作目录（首批）

直接映射 IRepositoryService 现有方法。目录即守卫测试的输入：Hidden 操作被 agent 通道调用必须拒绝，EachTime 永不出现"记住"路径，纯读永远不触发确认。

04

执行管线（所有出口共用）

请求携带来源与 agent 身份，五个挂点顺序执行。人自己的操作走既有交互，不经过确认队列——队列只是 agent 写请求的排队形态，策略同一张目录表。

请求(来源: ui | mcp | harness, 携带 agent 身份)
  → ① 可见性检查　Hidden + 非人来源 → 拒绝（审计记录）
  → ② 确认策略　Session 未记忆 / EachTime → 确认队列（§05）
  → ③ 安全网拦截　写操作 · §4.2 同库规则 · 阻止/警告分档
  → ④ 执行　GitWorker 入队，短生命周期仓库句柄
  → ⑤ 溯源 + 审计　trailer 打戳 / audit.jsonl → 结构化结果
三处收敛：§7.2 MCP 工具清单改由目录生成（加工具 = 加一行）；§12.3 harness 的 gitWrite 白名单改引用操作 id；§4.2 安全网从"提交时机的功能"重定位为"写管线拦截器"。规则库本身不变。
05

写路径：确认通道 · 溯源 · 审计

统一确认队列（人机同权）

有任务卡的进任务卡内联授权卡（不抢焦点）；无任务卡降级为变更页横幅 + 命令面板角标。队列积压 → 会话进入 AwaitingPermission 徽标态。

✓ 批准 ✕ 驳回 ⭑ 本会话记住

"记住"仅 Session 档出现；EachTime 档按钮不出现——高危操作没有记忆后门。

溯源与审计分离

进 git 数据（沿 §5.2 不扩）：
Assisted-by: <agent-id> · Gitter-Session: <uuid>
MCP 通道身份取握手 clientInfo，harness 通道取 manifest identity。

不进 git 数据：通道、确认人、耗时 → audit.jsonl。出问题时"谁在何时经哪条通道动了什么"有账可查。

诚实边界：agent 绕过 Gitter 直接跑 git（进程内自有行为）不受管线约束。对策不变：Codex sandbox 默认 workspace-write + preamble 软约束 + 验收台弱标注兜底。工具面管"经 Gitter 的"，验收台管"没经 Gitter 的"——两层防线各司其职，不伪装强隔离。

07

闭环：两通道、一状态

人的裁决与反馈通过两个通道喂给 agent，但状态只有一份——不出现"反馈双份、裁决两套"。

推 · harness 通道

人点"退回重做"，agent 会话在场

SubmitFeedbackAsync（NextTurn · exec resume）
拉 · MCP 通道

agent 主动查询（会话不在场 / 自主循环中）

review.state.read · review.submit_feedback
⟶
review.state + ReviewFeedback 列表（唯一一份）

人标 rejected + 写反馈 → 推通道起修复轮
修复轮中 agent 拉通道核对剩余 rejected 项
→ turn.completed → 宿主 checkpoint → 人继续审

CLI 出口兜底：gitter mcp serve · gitter repo <op> · gitter session <id> status · gitter task list——同一目录的文本投影，给不能挂 MCP 的 agent（脚本、CI）。无头环境 Session 确认降级为 --yes 显式旗标 + 审计标记 unattended。

场景走查（融合咬合点）

场景 1

旗舰闭环 · harness 在场（Codex）

每一步人与 agent 都咬合同一张目录
新建任务：拉出 task/<slug> worktreerepo.worktree.write · Session
派活给 Codexharness 出口 · 不涉目录
Codex 改文件——绕过 Gitter，sandbox 兜底管线外 · 诚实边界
轮次结束 → 宿主托管 checkpoint，trailer 齐全task.checkpoint · Hidden
人审：接受 → review.state 置 acceptedrepo.apply_patch · Session
人审：退回 + 写反馈 → rejected → 推通道直投reverse apply → SubmitFeedbackAsync
agent 拉通道核对剩余 rejected 项，精准修复review.state.read · RO
整理为一次提交（影响面数据来自 repo.impact）repo.history.write · EachTime
合并清理任务repo.worktree.write · EachTime
场景 2

纯 MCP 客户端 · 不经 harness（如 Cursor）

没有任务卡，融合依然成立
自查：diff + 风险信号repo.diff · review.risk_signals · Auto
暂存：首次弹内联卡，批准后本会话记住repo.stage · Session
提交被安全网拦截：发现疑似密钥 → 阻止repo.commit · 管线 STEP 3
agent 收结构化错误 → 改写 message 去掉密钥行 → 二次提交 → 人批repo.commit · Session
溯源 + 审计：Assisted-by: cursor（握手 clientInfo）+ Gitter-Session管线 STEP 5
场景 3

agent 全部离场（降级守卫）

拔掉所有 agent，Gitter 仍是完整 git 客户端
Hidden / RW 标注不影响任何 UI 操作；确认队列空；审计无 agent 行；MCP 关闭
守卫测试断言：禁用全部 harness 包 + 关闭 MCP 后，UI 出口对每个 Operation 的行为与引入工具面之前逐项一致

10

明确不做 & 文档关系

✕不做 agent 编排 / 工作流引擎 / 多 agent 调度——Gitter 不成为 agent 框架
✕不做工具的动态注册——目录静态、可审计、随版本发布
✕裁决、审计、反馈不写进 git 数据——trailer 白名单之外零污染
✕不为 agent 开放任何 Hidden 操作的特权模式；EachTime 无记忆后门
✕不做 MCP 之外的第三方工具协议适配——需要时它们也只是目录的新投影
