# Gitter 功能全面插件化重构方案（拆与不拆的裁决书）

> 状态：方案 v1（2026-10-06，仅方案未实施）
> 前置：extension-system-v2.md 36 条接缝已全部开缝并审计归零；agent-harness A1–A4 已落地
> 问题：按既有插件框架，UI 与 Gitter 功能哪些能拆成插件、哪些不能拆、为什么
> 方法：对全部内置功能逐项过四条判据（§一），产出能拆清单（§三，含机制映射与前置缺口）、不能拆清单（§四，五类理由）与迁移路线（§五）

---

## 一、判定框架：四条判据

对任一内置功能，依次回答：

1. **自举可行吗**——该功能能否用自家接缝（L0 数据 / L1 声明 / L2 受信代码 / L3 隔离）等价表达？表达不了的直接进"不能拆"。
2. **禁用不残废吗**——用户禁用/卸载该插件后，Gitter 是否仍是一个完整的 git 客户端？核心身份功能（没了它产品就不成立的功能）不拆。
3. **拆了降级吗**——过通用接缝后，性能 / 交互密度 / 类型安全是否明显劣化？渲染密集与高交互密度的东西不拆。
4. **信任边界对吗**——该功能是否属于"权限系统要保护的对象"？保护者不能被拆成被保护者。

另有一条**方向性铁律**：拆分方向永远是"宿主功能 → 插件"，且内置实现优先走自家接缝（自举）。凡插件能用的能力，宿主自己必须先走同一接缝——这既是 dogfooding 验证，也保证"禁用内置插件 = 回退到宿主缺省"语义清晰。

## 二、现状基线：已经是插件的（无需再拆）

主题（含默认双主题 + 5 个 tm 主题）、语法高亮、命令注册表（内置 25 条命令已走 CommandReg 自举）、右键菜单/快捷键、技能、安全网规则包机制、终端档位、空状态提示、模型端点、外部 MCP 声明、git 维护命令包（gitui.tools.git）。这些已完成"功能插件化"的第一阶段。

## 三、能拆清单（按迁移批次）

### PR-1 安全网正则规则 → L0 数据包（成本最低，语义最纯）

- **拆什么**：safety.ts 中 DEBUG_PATTERNS 表（console.log/breakpoint/dbg! 等按扩展名的调试残留正则）迁出为内置包 `gitui.safety.debug`（contributes.safetyRules，warning 档）
- **不拆什么**：密钥类 blocked 规则（私钥块/AKV/GitHub token/JWT/明文赋值）的**判定逻辑**留在宿主——它们是多模式组合 + KV 占位符豁免的代码逻辑，不是单条正则；大文件/二进制检查（结构性统计）留宿主；注释行豁免逻辑留宿主
- **理由**：规则数据与裁决引擎分离（§16.5 safetyRules 接缝的既定设计——数据包只有提示权，blocked 裁决权在宿主）；调试残留规则恰是"用户可能想定制"的部分
- **前置**：无（safetyRules 接缝已就绪）
- **验收**：删除 safety.ts 的 DEBUG_PATTERNS 后，.js 文件 console.log 仍被内置包标 warning；安全网冒烟不回归

### PR-2 AI 提交信息 / AI 解释 → L2 "AI 助手"包（价值最高，需补一个宿主缺口）

- **拆什么**：`ai.generateCommitMessage` / `ai.explain` 两个 RPC 的业务逻辑（prompt 构造 + 隐私分级 + 结果清洗）+ ChangesPage 的三个 AI 按钮入口，迁为 L2 插件 `gitui.ai.assistant`：
  - prompt 构造（buildCommitMessagePrompt/buildExplainPrompt）→ 插件代码（prompts 是产品语义，不是引擎）
  - 按钮入口 → `ctx.registerCommand`（命令面板）+ `ctx.registerCommitBlock`（提交框提示）表达
- **不拆什么**：ai.ts 的传输层（provider 注册表 + fetch + 密钥 safeStorage）留宿主——**apiKey 永不进插件**（§16.3 不变量）；隐私分级（metadataOnly 不出 diff）的执行点在宿主侧 git 读出口
- **前置缺口（必须先补）**：L2 ctx **没有 `ctx.git` 只读 API**（host.ts 有 currentRepo 和注释，实现缺失——L3 有 git.read 能力，L2 反而没有）。补 `ctx.git.status/diff/log`（只读，复用 L3 的 gitRead 实现），这是本方案唯一的宿主新增
- **隐私不变量**：插件经 ctx.git 拿到的 diff 受宿主隐私档位过滤（宿主在 ctx.git 出口执行 metadataOnly 裁剪），插件自己拿不到全量 diff 的绕过路径
- **验收**：禁用 gitui.ai.assistant 包后，Changes 页 AI 按钮消失（命令与区块来自插件），AI 设置页仍可用（传输层在宿主）

### PR-3 内置技能包 → L0（顺手）

- **拆什么**：提交信息规范（conventional commit 前缀建议、72 字符等规则文本）从 prompts.ts 的硬编码指令抽为内置技能包 `gitui.skill.commit-style`
- **理由**：prompt 规则是典型的"用户可定制"数据；skills 接缝现成
- **注意**：prompts.ts 保留缺省行为（技能包未装时不退化），技能为增量注入

### PR-4 更多散落动作命令化（L1 扫尾）

- **拆什么**：散落在各页面的低频动作收敛进命令注册表的 L1 贡献（如"复制仓库路径"、"在资源管理器显示仓库"）——扩 `gitui.tools.git` 或新增 `gitui.tools.workspace`
- **边界**：仅限白名单动作（terminal.run/shell.openPath/shell.reveal/repo.refresh）能表达的；涉及页面状态机的不动

### PR-5（可选）图片预览器 → L2 previewProvider

- preview.readPreview 已是"插件优先、内置兜底"架构；图片预览可作为内置 L2 插件迁移。**建议暂缓**：收益低（用户无定制需求），且 L2 禁用后图片预览消失属于降级——不满足判据 2，除非宿主保留最简图片兜底

## 四、不能拆清单（五类理由）

### A 类：自举死结（拆它 = 插件系统本身无法启动）

| 功能 | 理由 |
|---|---|
| 扩展系统自身（PackageStore/schema/registry/host/tools/events） | 插件的定义者与装载者。主题要加载器、命令要注册表——用插件实现插件系统是循环依赖 |
| 设置存储（settings.ts） | 信任门开关（allowCodePlugins 等）存在这里；插件自己的配置也存这里。拆它 = 信任门自己不可信 |
| i18n 宿主层 | 设置页语言选择是其它一切的前置；插件 i18n（%key%）消费宿主字典 |

### B 类：权限系统的"执行权"侧（§16.3 不变量的保护者不能变成被保护者）

| 功能 | 理由 |
|---|---|
| git 写操作流（changes.stage/commit、branches.* 写、push RPC） | 这些是权限系统看守的金库。拆成插件 = 被保护者自己拿着钥匙；且它们承载人审门 + 安全网 + 确认弹窗的执行语义 |
| 人审门（requestHumanApproval / pendingApprovals / 授权卡） | 安全不变量的执行点。门必须比门卫更不可拆 |
| 安全网**裁决器**（blocked 判定、豁免逻辑、scan 编排） | 数据规则可拆（PR-1），裁决权不可拆——恶意规则包不能获得拦截提交的权力 |
| checkpoint / 会话持久化（agents/session.ts） | agent 行为的审计账本。"全程时间线可溯"要求账本写入方不是被审计的插件 |

### C 类：性能关键渲染路径（判据 3）

| 功能 | 理由 |
|---|---|
| DiffView/DiffCanvas（字级 diff、虚拟滚动、并排/内联） | 每帧滚动都在跑的代码；过通用接缝（RPC 数据供给/iframe）会引入帧级开销与交互降级。这是产品核心体验差异点（设计文档既定） |
| 虚拟列表 / LogPage 时间轴 | 同上；万级提交滚动性能 |
| 终端（node-pty 会话管理） | 120fps 输出吞吐 + ConPTY 生命周期管理；插件档位已开放（数据面），引擎不拆 |

### D 类：骨架与导航（宿主 Chrome 原生原则，§16.2 机制 4）

| 功能 | 理由 |
|---|---|
| App Shell（TitleBar/Sidebar/StatusBar 容器/路由/页面框架） | 插件进插槽（statusbar/面板/视图容器），不成为骨架。骨架插件化 = 禁用一个插件整个 UI 塌陷，违反判据 2 |
| SplitPane 布局系统 | 全局布局基础设施 |
| 项目页（Projects） | 会话管理的根：打开哪个仓库决定一切上下文，属于宿主生命周期 |
| 命令面板本体（CommandPalette 组件） | 面板消费注册表（数据可来自插件），面板自身是骨架 |

### E 类：深度集成行为（拆了要撕开页面状态机，收益为负）

| 功能 | 理由 |
|---|---|
| squash 会话聚合 / 分组（LogPage + sessions.ts） | 需要 Log 行级选中上下文 + git 写 + 会话状态机三方联动；L1 命令的静态参数表达不了行级上下文，L2 命令又拿不到页面内部状态。它是核心 UX 而非可定制点 |
| Agent 任务循环与会话（agents/loop/session/providers） | 方向反了：harness 是插件的**消费者**（工具/技能/循环注册表的宿主侧）。把 harness 拆成插件 = 执行权离开宿主，违反 §15 安全不变量 |
| MCP 管道宿主 | 外部 agent 的接入口，人审门的持有者 |
| git 引擎读层（gitexec/status/log/branches 的 RPC 编排） | 所有 ctx.git / 工具 / RPC 的公共底座；已是" everyone 的依赖"，拆出无受益方 |

## 五、迁移路线与宿主终态

| 批次 | 内容 | 宿主改动 | 规模 |
|---|---|---|---|
| PR-1 | 安全网调试规则 → 内置 L0 包 | 无 | 小 |
| PR-2 | **补 L2 ctx.git（唯一宿主新增）** + AI 助手 L2 包 + Changes 按钮切换 | ctx.git 三方法 + 隐私裁剪出口 | 中 |
| PR-3 | 提交规范技能包 | 无 | 小 |
| PR-4 | 动作命令化扫尾 | 无 | 小 |
| PR-5 | （暂缓）图片预览插件化 | 无 | — |

**宿主终态（拆分完成后的"最小内核"边界）**：
git 引擎读写层 ∪ 扩展系统自身 ∪ 权限执行侧（人审门/安全网裁决/checkpoint）∪ 渲染关键路径（DiffView/虚拟列表/终端）∪ App 骨架与导航 ∪ Agent 循环与会话账本 ∪ AI 传输层。其余一切——数据（规则/主题/语法/技能/档位/提示）、行为（命令/工具/provider/循环）、入口（菜单/键位/区块/面板）——皆为插件，内置实现只是"随包发行的第一个插件"。

**反验收红线**（拆分过程中任何一步触碰即回退）：人审门被绕过、隐私档位被绕过、禁用内置插件导致核心页不可用、日志时间线断链。

## 六、明确不做

- 不做"页面级插件化"（Log/Changes/Branches 成为可卸载插件）——判据 2 直接否决，且渲染接缝撑不起交互密度；
- 不做插件替换 DiffView 渲染引擎；
- 不做插件参与权限裁决（L2 扫描器可产 blocked 是既定信任模型的结果，不是缺口——它依赖 allowCode 审核渠道门）；
- 不为拆而拆：PR-5 类"能拆但无受益"的项保持暂缓，待真实需求出现再启动。
